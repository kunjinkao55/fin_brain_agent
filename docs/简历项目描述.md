## 一、项目定位与核心价值

FinBrain 的核心价值不是"用了 LLM"，而是设计了一套 **Harness 工程体系**，用代码计算、多 Agent 审查、确定性守卫、条件分支、Fallback 熔断等手段，把 LLM 的输出质量从"可用"提升到"可审计、可回测、可复制"。

**解决的问题**：直接调用 GPT 生成研报存在幻觉、不一致、无法审计、无法回测等问题。FinBrain 通过 Harness 工程体系，把 LLM 限制在"叙事生成"的边界内，确保输出的每一个数字都可追溯、可验证、可审计。

## 二、Agent 架构设计

### 2.1 LangGraph 8 节点流水线

```
用户输入（"分析国网信通600131"）
    │
    ▼
意图路由 → Chat / Deep Analysis / Phantom Hunter
    │
    ▼
┌─────────────────────────────────────────────────────┐
│  研究流水线（LangGraph StateGraph）                  │
│                                                      │
│  Data → Classify → Analyst → Valuation               │
│  (并行)   (Code)      (LLM)     (LLM)                │
│                                                      │
│  → Critics(三路并行) → Repair → Reporter → Audit     │
│     Logic/Finance/Industry  (LLM)    (LLM)  (Code)   │
└─────────────────────────────────────────────────────┘
    │
    ▼
结构化报告 + 执行 Trace + 审计摘要
```

### 2.2 核心 Agent 角色

| Agent | 职责 | 技术实现 |
|-------|------|----------|
| **Data Collector** | 并行预取财报、估值、行情、行业、公告、资金流量 | 多线程并发 + 缓存 + 失败重试 |
| **Company Classifier** | 纯代码提取公司特征，输出混合属性权重 | 财务指标计算 + 规则引擎 |
| **Analyst** | 生成投资分析报告（评分、估值、风险、操作建议） | LLM + 结构化输出（Pydantic schema） |
| **Valuation** | 判断公司阶段，推荐估值方法，输出多框架参考区间 | LLM + 结构化输出 |
| **Critics（三路并行）** | 逻辑/财务/行业审查，发现分析中的问题 | 三个独立 Critic Agent，覆盖不同盲区 |
| **Repair** | 根据 Critic 发现的问题，自动修正分析 JSON | LLM + 针对性修复 |
| **Reporter** | 生成最终报告，代码计算评分、估值、投资决策 | 代码计算 + LLM 叙事 |
| **Audit** | 审计最终报告，检查一致性和可执行性 | LLM + 代码预检 |

### 2.3 条件分支与错误恢复

LangGraph 条件分支让错误成为路径，而不是中断：

```python
# 数据不足 → 重取一次，充足 → classify
def route_after_data(state):
    if not has_symbol and data_attempts < 2:
        return "data_collector"  # 数据不足，重取
    return "classifier"  # 数据充足，继续

# Critic 通过 → 跳过 Repair，否则进入 Repair
def route_after_critic(state):
    if total_issues == 0:
        return "reporter"  # 无问题，跳过 Repair
    return "repair"  # 有问题，Repair 修复
```

## 三、Harness 工程体系

### 3.1 结构化输出 Harness

用 Pydantic schema 约束 LLM 输出，替代脆弱的 json.loads + 正则兜底：

```python
# 之前：脆弱的 json.loads + 正则兜底
raw = llm.invoke(prompt).content
data = json.loads(raw)  # 可能失败

# 之后：Pydantic schema + with_structured_output
structured_llm = llm.with_structured_output(AnalystOutput)
data = structured_llm.invoke(prompt)  # 输出稳定为 AnalystOutput
```

**核心模型**：
- `AnalystOutput`：分析报告（评分、估值、风险、操作建议）
- `ValuationOutput`：估值框架（公司阶段、适用框架、参考区间）
- `CriticOutput`：审查结果（通过、逻辑漏洞、财务误读、行业误述）
- `AuditOutput`：审计结果（通过、问题列表、修正建议）

### 3.2 代码计算 Harness

财务指标、评分、估值由代码计算，LLM 只负责叙事，确保数字 100% 准确：

```python
# 之前：LLM 自己算 PE、EPS、评分
"PE = 股价 / EPS"  # LLM 可能算错

# 之后：代码计算，LLM 只叙事
pe = code_calculate_pe(price, eps)  # 代码 100% 准确
"PE 为 {pe} 倍"  # LLM 只负责描述
```

**代码计算的指标**：
- 财务指标：ROE、毛利率、净利率、资产负债率、现金流覆盖率
- 估值指标：PE、PB、前瞻 PE、合理价值、安全买入价
- 评分指标：盈利能力、成长性、财务健康、估值合理、行业前景、资金认可

### 3.3 多 Agent 审查 Harness

Critic 三路并行 + Audit 审计，用 LLM 审查 LLM，减少单一视角盲区：

| Critic | 擅长发现的问题 | 盲区 |
|--------|----------------|------|
| **Logic Critic** | 投资逻辑矛盾、未经验证的假设、忽略重大风险 | 不擅长算财务数字 |
| **Finance Critic** | 财务数据矛盾（毛利率高但现金流差）、指标计算错误 | 不擅长判断行业趋势 |
| **Industry Critic** | 行业判断错误、竞争格局高估/低估、趋势误读 | 不擅长检查内部逻辑 |

**Repair 循环**：发现问题后 Repair Agent 修复，然后重新审查，形成闭环。

### 3.4 确定性守卫 Harness

9 项代码检查兜底数字和逻辑一致性：

| 检查项 | 说明 |
|--------|------|
| 事件-估值联动 | 有定增/摊薄事件时，合理价值是否已显式调整 |
| 评分-估值矛盾 | 成长性评分 <5 但乐观 PE >25 倍时警告 |
| 评级-操作一致 | 投资评级与操作建议是否一致 |
| 估值合理 | PE/PB 是否在合理区间，与行业基准对比 |
| 数据单位 | 金额单位是否统一（万元/亿元） |
| 评分合计 | 六维评分合计是否准确（代码生成，LLM 不参与） |
| 操作建议 | 是否包含可执行要素（价格、仓位、止损、持仓周期） |
| 情景 EPS 单调性 | 悲观 EPS ≤ 基准 EPS ≤ 乐观 EPS，价格 = EPS × PE 算术校验 |
| 时效性矛盾 | 业绩快报已发布但建议"等待半年报"时标记 ❌ |

### 3.5 Fallback Harness

3 槽位 LLM 熔断链，单点失败不导致整个流程失败：

```python
class LLMFallbackChain:
    def invoke(self, *args, **kwargs):
        for i in range(len(self.slots)):
            try:
                self._llm = _create_llm(self.slots[i])
                return self._llm.invoke(*args, **kwargs)
            except Exception:
                continue  # 失败，切换下一个槽位
        raise RuntimeError("所有槽位调用失败")
```

**支持的 LLM 提供商**：DeepSeek、OpenAI、Anthropic

## 十、技术深度说明（面试用）

### 10.1 为什么需要 Harness？

LLM 本身不是壁垒，Harness 才是壁垒：
- **确定性**：代码计算的数字 100% 准确，LLM 无法篡改
- **可审计**：每个数字都有来源，每个结论都有依据
- **可回测**：历史报告可以回测验证，持续优化
- **可复制**：Harness 是工程系统，不依赖特定 LLM

### 10.2 Harness 与 Agent 的区别

| 维度 | 普通 Agent | FinBrain（Harness 驱动） |
|------|------------|--------------------------|
| 核心 | LLM 的智能 | 工程的确定性 |
| 可靠性 | 依赖 LLM 能力 | 依赖多层防线 |
| 可审计性 | 黑盒，无法追溯 | 白盒，每个数字可验证 |
| 可维护性 | 依赖 Prompt 调优 | 依赖代码和规则优化 |
| 可扩展性 | 换 LLM 需要重新调优 | 换 LLM 只需改配置，Harness 不变 |

### 10.3 数据源的信任问题

FinBrain 的一切都基于"数据源可信"这个假设。但实际情况是，免费 API 数据可能滞后或错误。FinBrain 的聪明之处在于：它不假装数据源是可信的，而是通过数据质量校验、多源交叉验证、数据可信度提示等手段，让用户知道数据的可信度边界。

Harness 的真正价值不是"消除数据源的不确定性"，而是"当数据源可信时，保证输出质量；当数据源不可信时，提醒用户数据可信度"。

### 10.4 RAG 技术选型

**为什么用 ChromaDB + ONNX 而不是 Pinecone/Weaviate？**
- **本地化**：无需外部 API，数据不出本地，保护隐私
- **成本低**：ONNX 模型免费，ChromaDB 开源
- **速度快**：本地嵌入 + 本地检索，毫秒级响应
- **可定制**：可以自定义行业模板和会计规则

**为什么是动态 RAG 而不是固定知识库？**
- **行业差异**：不同行业的估值方法和会计规则差异巨大
- **时效性**：行业趋势和会计准则会变化，需要动态更新
- **精准性**：按行业注入模板，比通用知识库更精准

### 10.5 并发处理与线程安全

**为什么用 ThreadPoolExecutor 而不是 asyncio？**
- **简单性**：ThreadPoolExecutor 更适合 CPU 密集型和 I/O 密集型混合任务
- **兼容性**：与现有同步代码库兼容，不需要重写为 async
- **可控性**：max_workers 可以控制并发数，避免过载

**线程安全的挑战**：
- **Portfolio 状态**：需要 threading.Lock 保护，防止并发买卖导致数据不一致
- **工具调用计数**：需要 _call_lock 保护，防止计数器漂移
- **缓存访问**：需要模块级锁保护，防止缓存竞争

### 10.6 错误处理与恢复

**为什么用 LangGraph 条件分支而不是 try-except？**
- **流程可视化**：条件分支让错误成为路径，而不是中断
- **可测试性**：每个分支可以独立测试
- **可恢复性**：数据不足重取，Critic 通过跳过 Repair，流程不是固定的

**LLM Fallback 的设计**：
- **多槽位**：3 个槽位，slot 1 必填，slot 2/3 可选
- **熔断链**：连续失败时自动切换下一个槽位
- **结构化输出回退**：结构化输出失败时，回退到原始文本输出并手动解析
